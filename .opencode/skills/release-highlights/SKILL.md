# Release highlights

Draft releases are generated by semantic-release. Your job is the only human
part: the **intro highlight** at the top — short, straight to the point, and
readable by a layman, not by an AI or an engineer.

`release-notes` (`.opencode/skills/release-notes/SKILL.md`) owns the full
publish workflow and the long tone rules; this skill is the fast path for
drafting and applying one highlight message.

## Workflow

1. **Read the draft.**
   ```powershell
   gh release list --repo Belphemur/SoundSwitch --limit 10
   gh release view <tag> --repo Belphemur/SoundSwitch --json isDraft,body,tagName
   ```
   The draft body is (or should be) exactly the generated changelog section —
   treat it as **verbatim**: never reword the section, deduplicate its `closes`
   tags, or drop lines.
2. **Read the last 2–3 release bodies for tone** (`gh release view v7.4.1 …`,
   and betas of the previous minor). Voice: the maintainer's own — first
   person, short sentences, what users *observe*, no internal vocabulary, no
   AI-ish phrasing. A contributor gets named credit when their work ships
   (v7.4.0-beta.1 credited `@ampersandru`).
3. **Write the intro.** Rules, in order:
   - At most ~120 words. Three bold bullets on a beta/minor; two plain
     sentences on a patch.
   - Layman reading: name the surface ("General tab", "app-rules editor"),
     never the machinery ("PerMonitorV2", "AutoScaleMode").
   - End with the beta ask ("Beta as usual: give it a spin and tell me what
     breaks.") or upgrade advice on a stable release.
   - No emoji headers unless pairing with a significant release.
4. **Apply it: prepend the intro, keep the generated section verbatim.**
5. **Verify, then stop.** Re-run `gh release view <tag>` and check:
   - intro first, then one `## [<version>]` block, nothing else;
   - unicode survived (`—`, `–` intact — see gotcha);
   - the release is still a **draft**. Publishing is the maintainer's call;
     the publish steps live in `release-notes`.

## Gotchas

- **PowerShell 5.1 mangles unicode in inline command text.** Never pass the
  body or an em-dash through an inline multi-line command; write a small
  `.ps1` file (ASCII only in the script text itself) that reads the intro/new
  assets from files and runs `gh release edit <tag> --notes-file <file>`,
  then run it with `pwsh -NoProfile -File <script>` and verify.
- `gh` returns the body as an **array of lines** in PowerShell —
  `($draft -join "`n")` before concatenating, or the composed body loses its
  line breaks.
- The changelog section stays **exactly as generated**: deduplicating the
  `closes #n` references is tempting and not your edit to make.
