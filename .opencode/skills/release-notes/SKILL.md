# Release notes

SoundSwitch releases are generated by semantic-release: every merge to `dev`
extends `CHANGELOG.md` and creates (or updates) a **draft** GitHub release with
assets and a changelog-derived body. The human work is the release **body**:
an intro in the maintainer's voice, plus the generated changelog section,
verbatim.

## Where things come from

| Artifact | Source | Notes |
| --- | --- | --- |
| `CHANGELOG.md` latest section | semantic-release, automatic | Never hand-edit; copy the whole `## [<version>]` block verbatim. |
| Draft release body | semantic-release on CI | Sometimes leaks the **previous** release's section - that is the leak you rewrite. |
| VirusTotal analysis block | ghaction-virustotal, **automatic** | Never write it yourself; it appends after publishing. |
| Intro/highlights/fixes | You | The only prose you author; see tone rules. |

The release commit itself lands on `master` (`chore(release): X.Y.Z [skip ci]`);
`dev` carries the fixes ahead of it.

## Workflow

1. **Inspect the pending release.**
   `gh release list --limit 10 --json tagName,isDraft,name` then
   `gh release view <tag> --json body,isDraft,assets`. Confirm:
   - the body opens with a **stale** section (the 7.4.1 draft opened with the
     7.4.0 section) - that is the leak you rewrite;
   - assets match the version (`SoundSwitch vX.Y.Z.0_Release_Installer.exe`,
     the `_arm64.exe` sibling, and `SoundSwitch-vX.Y.Z.zip`).
2. **Read the last ~10 release bodies for tone** - the voice is the
   maintainer's own: first person, short, direct, practical about upgrading.
3. **Extract the changelog block.** In PowerShell, isolate the latest section
   without touching `CHANGELOG.md`:
   ```powershell
   $ch = Get-Content CHANGELOG.md -Raw
   $m = [regex]::Match($ch, '(?s)## \[7\.4\.1\].*?(?=\r?\n## \[7\.4\.0\])')
   $section = $m.Value.TrimEnd()
   ```
4. **Write the intro** per the tone rules below, then append the changelog
   section and update the draft:
   ```powershell
   gh release edit v7.4.1 --notes-file <bodyfile>
   ```
5. **Verify** `gh release view <tag> --json body` - intro first, one `##` for
   your prose, the `## [version]` block, *no* older versions, nothing about
   VirusTotal. Then publish when the decision to release has been made:
   ```powershell
   gh release edit v7.4.1 --draft=false
   gh release list --limit 3   # confirm "Latest" moved
   ```
   The VirusTotal analysis block appears automatically after that; do not add
   shields or links by hand.

## Tone rules (from the last 10 releases, keep them fresh)

- **Patch releases**: one or two short first-person sentences before the
  changelog - what broke, what this fixes, and upgrade advice when warranted
  (v7.3.2: "Strongly advise to update to this." for a bug affecting many
  people).
- **A regression snuck in**: say so plainly and apologise once (v7.3.1: "Sorry
  for having so many releases, but I thought I had fixed..."). Do not
  editorialise beyond that.
- **Minor/feature releases**: `## ✨ Highlights` (bold capability - em-dash -
  one user-level line, `(#issue)` only when it tracks a long-standing ask),
  `## 🐛 Fixes` in plain language, and a `## 💜` thanks section when a
  contributor's work ships (name the user, say what they contributed).
- **Beta releases**: a short paragraph crediting the contributor and what to
  try, before the changelog block.
- Talk about what **users can observe** ("Saving your settings survives a
  locked configuration file"), never internal vocabulary ("atomic swap under
  `SaveLock`").
- Sentry/telemetry counts are fine as justification ("~300 affected users"),
  matching the repo's telemetry-driven practice.
- Emoji `##` headers are welcome on significant releases; patches can be a
  plain two-liner (v7.3.3).

## Gotchas

- **PowerShell 5.1** mangles unicode here-strings and rejects `utf8NoBOM`;
  write the body file with `[System.IO.File]::WriteAllText($path, $body,
  [System.Text.UTF8Encoding]::new($false))` and build emoji from code points
  (`-join ([char]0xD83D, [char]0xDC1B)` for 🐛). Re-verify the `##` headers
  with `gh release view` - a `## ??` header means the emoji got mangled.
- The changelog **block** is the only section kept verbatim; the issue/commit
  links and `closes #...` references keep the tracking auditable.
- Do not run `documentation-sync` for a release body change; that skill is for
  feature/docs drift, not release announcements.
